# Modelo físico PostgreSQL 16

Estado: `DRAFT_CANDIDATE_FOR_HUMAN_REVIEW`. Esta es una pseudodefinición no ejecutable; deliberadamente no usa sintaxis DDL.

## 1. Cómo interpretar el diccionario

Una tabla queda definida por su **perfil** más las columnas propias de su fila. Notación: `!` = NOT NULL, `?` = NULL, `=x` = default autorizado. Toda columna sin `=x` carece de default. Todas las PK son UUIDv7 opacas generadas por plataforma. El propósito de cada tabla canónica es ser la persistencia autoritativa de la entidad indicada después de `—`, dentro del bounded context del encabezado y con la responsabilidad exacta trazada en 12; las filas “support/relación” sólo normalizan el contrato citado y no adquieren autoridad de negocio.

### 1.1 Perfiles de columnas

| Perfil | Columnas obligatorias |
|---|---|
| `M` mutable | `<pk> uuid!`; `created_at timestamptz!=CURRENT_TIMESTAMP`; `created_by_user_identity_id uuid?`; `created_by_service_principal_id uuid?`; `updated_at timestamptz!=CURRENT_TIMESTAMP`; `updated_by_user_identity_id uuid?`; `updated_by_service_principal_id uuid?`; `row_version bigint!=1`; CHECK actores `at most one`; CHECK `row_version>0` |
| `TM` tenant mutable | todas `M` + `tenant_id uuid!`; FK `tenant_id→platform.tenants`; UNIQUE de soporte `(tenant_id,<pk>)` |
| `I` inmutable/append-only | `<pk> uuid!`; `created_at timestamptz!=CURRENT_TIMESTAMP`; `created_by_user_identity_id uuid?`; `created_by_service_principal_id uuid?`; CHECK actor `at most one`; sin `updated_*` |
| `TI` tenant inmutable | todas `I` + `tenant_id uuid!`; FK tenant; UNIQUE `(tenant_id,<pk>)` |
| `V` versión global/plataforma | todas `I` + `<root_fk> uuid!`; `version_number bigint!`; `lifecycle_state varchar(32)!`; `effective_from timestamptz?`; `effective_to timestamptz?`; `published_at timestamptz?`; `superseded_by_id uuid?`; UNIQUE `(<root_fk>,version_number)`; CHECK intervalos y publicación |
| `TV` versión tenant | todas `V` + `tenant_id uuid!`; FK compuesta al root; UNIQUE `(tenant_id,<root_fk>,version_number)` y `(tenant_id,<pk>)` |
| `MX` ownership mixto | todas `M` + `ownership_class varchar(24)!`; `tenant_id uuid?`; CHECK clase en `GLOBAL_REFERENCE, PLATFORM_CONTROL, TENANT_OWNED, TENANT_DERIVED`; CHECK tenant obligatorio sólo para `TENANT_*`; UNIQUE `(tenant_id,<pk>)` parcial/lógico para soporte FK |
| `MXI` ownership mixto inmutable | todas `I` + `ownership_class varchar(24)!`; `tenant_id uuid?`; mismo CHECK de ownership |
| `EV` evento/audit/outbox | todas `I` + `ownership_class varchar(24)!`; `tenant_id uuid?`; `correlation_id uuid!`; `causation_id uuid?`; mismo CHECK de ownership |

Todos los perfiles con `tenant_id` aplican FKs compuestas en relaciones TENANT_*; los `created_by/updated_by` son metadata, mientras `ops_audit.audit_events` es la autoridad de reconstrucción. `effective_to > effective_from`; intervalos abiertos usan NULL. Defaults distintos de timestamps técnicos, booleanos explícitos y contadores cero sólo aparecen cuando la semántica los autoriza.

### 1.2 Códigos de política

`AO=ARCHIVE_ONLY`, `SV=SUPERSEDE_VERSION`, `IV=INVALIDATE`, `IR=IMMUTABLE_RETAIN`, `PE=EPHEMERAL_PURGE`, `PEC=PRIVACY_ERASURE_CONTROLLED`. Retención `POL` significa resolver `privacy.retention_policies`; valores fijos se indican expresamente.

## 12. Integridad global de perfiles

1. Toda FK entre tablas `T*` incluye `tenant_id` y referencia una clave `(tenant_id,id)`, salvo referencias explícitas a GLOBAL_REFERENCE/PLATFORM_CONTROL.
2. Toda tabla `MX*` aplica el CHECK ownership/tenant del perfil y valida que los padres mixtos tengan ownership compatible.
3. Una versión publicada no se actualiza; se crea nueva identidad/version y `superseded_by_id` conserva historia.
4. `row_version` soporta optimistic concurrency sólo en tablas editables; append-only/versiones publicadas no se actualizan.
5. Ninguna FK histórica usa `ON DELETE CASCADE`; las políticas de borrado están en 06.
6. Checks que requieren varias tablas (publicación con coverage 100, SoD condicional, transición autorizada, selected subset, metodología efectiva) se verifican transaccionalmente en el futuro backend y se auditan; 03 los clasifica expresamente. No se autorizan triggers en esta fase.
