## MFA proof profile and acceptance decision

Minimum external ID-token claims for identity proof are signed `iss`, stable `sub`, client-bound `aud`, `iat`, `exp`, and the existing nonce/state/code validation. The future adapter also requires **verified password and TOTP authentication evidence** from the specific Keycloak authentication session consumed by GRC. Keycloak's configured AMR execution references and ACR/LoA mapping are candidate sources, but MI4–MI8 must pin the exact versioned flow/mappers and demonstrate that their signed claims mean successful factor execution. GRC must verify issuer, audience, signature, algorithm, time, nonce, subject, expected authentication context and factor evidence; it must not infer MFA from the user having a TOTP credential. First enrollment without a subsequent verified TOTP challenge must DENY. An SSO cookie must not turn a previously enrolled factor into proof of a newly claimed MFA execution. If the selected Keycloak configuration cannot provide this evidence reliably, integration remains blocked; no provisional password-only path is allowed. Keycloak access/ID tokens are never API bearer tokens. The GRC TCDX JWT retains canonical `UserIdentity` UUID as `sub` and does not copy provider roles or tenant permissions.

MI5A closed the versioned proof profile on Keycloak 26.7.5: browser flow `tcdx-browser-password-totp` has REQUIRED `auth-username-password-form` and REQUIRED `auth-otp-form`, with execution references `pwd` and `otp`; Cookie is DISABLED. The native `oidc-amr-mapper` emits `amr` in the signed **ID token**, not the access token. A real verified password plus TOTP login produced `amr=["pwd","otp"]`; the enrollment token produced `amr=[]`; password-only and invalid OTP did not produce a completed login token. The backend must validate the ID token signature/JWKS, exact issuer, exact client audience, time, nonce, subject and session context before requiring an AMR array containing both references. `acr` alone, Keycloak roles/groups and editable user attributes are never MFA proof. This proof establishes the MI5 adapter contract, not GRC runtime validation.

MI5-R uses confidential OIDC client `tcdx-grc`, exact issuer `https://iam.grc.tecdex.net/realms/tcdx-managed-identity`, ID-token audience `tcdx-grc`, and callback `https://grc.tecdex.net/auth/callback`. It uses Authorization Code + PKCE S256 through existing `/auth/login?provider=tcdx-managed-identity` and `/auth/callback` routes. The client has no browser web origins or post-logout redirect; GRC currently performs local application logout. The secret is held in a protected external file, not versioned. Unknown or inactive `UserIdentity` is DENY by exact issuer+subject identity key; all tenant and Platform grants remain in GRC. No GRC schema change is required.

## Lifecycle and infrastructure gates

### MI6A — human-approved Platform administrative contract (2026-10-01)

This section is the separate executable approval required by the ADR and the MI6 plan. It authorizes a **future** MI6 implementation, not a runtime permission publication, account creation, Keycloak configuration, migration or deployment. Managed Identity and its credentials are global to a person who may have memberships in several tenants. Every operation below therefore requires an active canonical `UserIdentity` actor with an active `PlatformRoleAssignment` to `PLATFORM_ADMIN`, the exact listed Permission with `platform` scope, object policy and SoD; default DENY applies. A Tenant Admin, Platform Support, a Keycloak role/group, an OIDC claim or a tenant header never substitutes for that chain. `X-TCDX-Tenant-Id` on these Platform-only routes is rejected with `TCDX.AUTHORIZATION.DENIED`; `tenant_id` in query/body is invalid input. No tenant is fabricated in GRC audit or idempotency scope.

The approved Permission resource is `platform.managed_identity` in `CORE_PLATFORM`, with `read`, `create`, `update` and `administer` actions. The registry's rector 22 §10 resource list is **initial**; its `platform` domain already permits all four actions and the human MI6A decision publishes this additional resource, as prior human amendments published other Platform resources. `PLATFORM_ADMIN` is the sole initial base-role grant; there is no new role and no Tenant Admin or Platform Support grant. `update` is limited to future nonsecret metadata changes, but **no update operation is published in MI6A** and possession of this Permission alone authorizes no route or Keycloak action. Runtime catalog rows and role grants await MI6 materialization under the existing physical model.

All paths below are relative to `/api/v1`; IDs are canonical `iam.user_identities.user_identity_id` UUIDs, never username or Keycloak subject in the path. The command suffix matches the existing v1 command convention. Only the eight operations in this table are approved:

`managedIdentityProvision` accepts only a nonblank individual `display_name`, nonblank `username`, a nonsecret `person_verification_ref` for the completed operator-to-person check, and optional `email` attribute. The operator must first identify the named person; the reference is metadata, never a credential or a substitute for the check. No tenant, role, permission, grant, lifecycle override, subject, credential, MFA seed or caller-selected provider is accepted as business input. The configured exact issuer plus Keycloak immutable subject resolves or creates **one** canonical `UserIdentity` through the existing identity mechanism; identity uniqueness and Keycloak username uniqueness are mandatory. Provisioning does not call `membershipCreate`, `membershipRoleAssign` or PlatformRoleAssignment grant. A provisioned identity, even after password and verified TOTP, has no GRC authority without separate canonical grants. The human MI6F decision defines one-time access as **one plaintext disclosure in the original authorized HTTPS success response plus Keycloak's forced password change at first login**. It does not assert time-based expiration of a Keycloak temporary password. The Platform operator delivers the credential to the identified person through an external authorized out-of-band channel; GRC implements no email, mailbox or other end-user delivery channel.

List uses the existing bounded cursor pagination (default 25, maximum 100) and returns only globally authorized minimal metadata. Read and list may expose canonical identity UUID, provider, exact issuer, opaque subject reference, username, safe lifecycle/enabled and MFA-enrollment metadata. They never expose password/verifier, temporary credential, TOTP seed/code, recovery secret, client secret, raw OIDC token, or arbitrary memberships. Membership enumeration requires its separate published Permission and operation. `platform.managed_identity.update` cannot be used as an alternate credential command.

Each sensitive command requires a nonblank `reason` of at most 2000 characters; reads and provision do not require it. Password reset additionally requires a nonsecret `person_verification_ref` for the direct recovery handoff. Password reset invalidates the prior credential and sessions, forces a new password and preserves the mandatory TOTP gate. MFA reset invalidates the old factor and sessions, requires a fresh enrollment and verified challenge, and reveals no prior seed. Recovery without mailbox is authorized Platform operator password reset plus MFA reset when needed, followed by the same human ceremony; it is **not** a ninth API operation. Disable denies later login and invalidates sessions; enable alone creates no authenticated session or GRC grant. Session revoke invalidates Keycloak sessions **and** any still-valid TCDX application sessions/tokens for this identity under the existing revocation policy; the same global application-session invalidation applies to disable, password reset and MFA reset. A provider logout alone cannot be reported as complete GRC revocation. Self-service password change stays in Keycloak's authenticated user lifecycle and is not a GRC admin command.

Every POST requires `Idempotency-Key` scoped to `PLATFORM_CONTROL + actor UserIdentity + operation + key + canonical request hash`, with no tenant. Same key and payload replays the result without a second Keycloak action, canonical UserIdentity, audit or credential; same key with different payload returns `TCDX.CONFLICT.IDEMPOTENCY`. Username uniqueness and exact issuer+subject uniqueness fail closed; a different key cannot silently adopt an existing username. Because Keycloak and PostgreSQL cannot share one ACID transaction, an uncertain upstream outcome must be reconciled against the same immutable Keycloak user and canonical identity before retry. It must never create a second user, repeat a credential-changing action, or claim success without the corresponding GRC audit/idempotency outcome. MI6 must prove the crash/retry reconciliation using only approved persistence; inability to do so blocks implementation rather than introducing a new schema or weaker semantics.

Each successful mutation writes exactly one operation-specific GRC `AuditEvent` with actor, target canonical identity (when known), operation, server time, outcome, correlation, safe before/after state and required reason, under `PLATFORM_CONTROL` with `tenant_id=NULL`. No GRC domain outbox event is published absent a separately approved downstream fact; Keycloak persists its own user/admin credential and authentication events. Denials and failures use the existing safe security-audit policy. The audit and all telemetry exclude credentials, TOTP material, token values and provider payloads. No Keycloak realm/client role or group can confer GRC Permission.

Use the existing error taxonomy: `TCDX.AUTHENTICATION.REQUIRED/INVALID` (401), `TCDX.AUTHORIZATION.DENIED` (403), `TCDX.RESOURCE.NOT_FOUND` (404, including concealed targets), `TCDX.CONFLICT.RESOURCE` (409, duplicate username or issuer+subject), `TCDX.LIFECYCLE.TRANSITION_DENIED` (409, invalid account state), `TCDX.CONFLICT.IDEMPOTENCY` (409), `TCDX.VALIDATION.FAILED` (400), and redacted `TCDX.PROVIDER.FAILURE` (502) or `TCDX.DEPENDENCY.UNAVAILABLE` (503). MI6F adds the conflict-class `TCDX.CONFLICT.RECOVERY_REQUIRED` (409, `retryable=false`) for an uncertain credential-changing outcome that must not be retried automatically. No Keycloak error body, secret, or foreign identity existence is disclosed.

### MI10 R3 — bounded AMR execution evidence (2026-10-07)

The versioned policy is `iam/config/managed-identity-amr-policy.json`. Both REQUIRED factor executions retain their native `default.reference.value` (`pwd` and `otp`) and set native `default.reference.maxAge` to the existing GRC browser authentication transaction limit, 600 seconds. Keycloak 26.7.5 otherwise defaults this native reference validity to zero seconds and removes password evidence while a person completes TOTP. This bounded claim-generation setting changes no backend acceptance rule: signed ID-token evidence must still contain both successfully executed factors from the current session; Cookie remains DISABLED, first enrollment alone remains insufficient, and issuer/audience/signature/time/nonce/state/PKCE validation is preserved. Expired factor references remain absent and denied. It grants no realm-management privilege to the user provisioner.

### MI6F — temporary credential disclosure and uncertain-result contract (2026-10-02)

The human architecture/security approval permits the GRC backend to generate a cryptographically strong temporary credential for `managedIdentityProvision` and `managedIdentityPasswordReset`. Keycloak remains the credential and verification authority. GRC supplies the plaintext only to Keycloak's temporary-password action and, after the respective success boundary below, to the initiating authorized Platform Admin **once in the original HTTPS response**. `ManagedIdentityCredentialOperationResult` is the common response for these two operations: it contains the safe identity projection and `credential_disclosed`; only an original success with `credential_disclosed=true` contains `temporary_credential`. A reconciled same-key replay has `credential_disclosed=false` and no `temporary_credential`. `Cache-Control: no-store` is required on both success and recovery responses. The credential is never persisted in GRC DB, supplementary Keycloak metadata, idempotency, audit, files, logs, access logs controlled by the application, reports, traces, telemetry, frontend persistent storage, cookies or caches. Response/request body logging and telemetry capture of the value are prohibited.

The credential's one-time property is **one disclosure plus forced change**, not guaranteed expiry after a fixed number of minutes. The Platform Admin handles direct delivery to the named human through an authorized external out-of-band channel outside GRC. GRC does not implement email, SMS or messaging delivery. The operator's browser may hold the value only in volatile memory for the current view; refresh or navigation cannot recover it. MI7 may implement an explicit copy action, but may not put it in localStorage, sessionStorage, IndexedDB, persistent state, analytics, console logs, error payloads or deliberate browser cache. Automatic clipboard clearing is not claimed.

The existing `Idempotency-Key` binding remains `PLATFORM_CONTROL + actor + operation + key + canonical request hash`, without tenant. An in-progress claim must be durable before a Keycloak mutation. Same-key/different-hash remains `TCDX.CONFLICT.IDEMPOTENCY`; a concurrent in-progress request cannot perform a second provider action. Successful same-key replay returns only reconciled nonsecret metadata, marks `credential_disclosed=false`, and neither regenerates nor rediscoses the credential. No secret or secret-derived replay body/hash may be stored to make this possible. The original response may disclose only while the backend retains the generated value in volatile memory for that request. This rule specializes the normal persisted-result replay: the durable result is the safe identity/result reference, not the transient disclosure.

`UNCERTAIN_RESULT` means the backend cannot prove whether Keycloak completed a sensitive mutation before an interruption. It neither claims success nor failure, repeats the mutation, retrieves a prior plaintext, nor discloses one. The API returns the standard `application/problem+json` envelope with `code=TCDX.CONFLICT.RECOVERY_REQUIRED`, HTTP 409 and `retryable=false`; its safe message directs an authorized operator to reconcile or initiate a fresh approved recovery. Audit records an uncertain/recovery-required outcome, actor, target when known, operation, reason when required, correlation and idempotency reference without a credential. A replay of the same key may return proven safe metadata or this recovery error, never a second credential action.

Provision success requires **both** a confirmed Keycloak user with immutable subject and a committed canonical `UserIdentity` for exact issuer+subject, together with the operation's safe audit and completed idempotency outcome. Password-reset success with disclosure requires Keycloak confirmation of the temporary-password action, the corresponding safe GRC audit/idempotency outcome, and the original request still holding its plaintext only in memory. If any success predicate cannot be proven, no credential is disclosed. A lost or uncertain credential cannot be recovered. A later authorized `managedIdentityPasswordReset` with a **new** key generates a new temporary credential and replaces the old Keycloak password; same-key replay does not. This uses the existing eighth-operation set and no distributed transaction, escrow, new endpoint, table or migration.

### MI6F-R — approved Provision reconciliation marker (2026-10-02)

The human architecture decision approves exactly one internal technical user attribute, `tcdx_provision_reconciliation_marker`, for `managedIdentityProvision`. Before the Keycloak user-create call, the GRC backend generates a fresh opaque value from its runtime CSPRNG with at least 128 bits of random entropy. The marker is independent of username, email, tenant, business/personal data, UserIdentity ID and the plaintext `Idempotency-Key`; it is not supplied by the client or derived from any of those inputs. It is nonsecret technical metadata, never a credential, external identity key, authenticator, tenant/RBAC fact or response field. Knowledge of it grants no access. It is never mapped into OIDC tokens, displayed in UI, reported as business data or made editable. The existing `ops_audit.idempotency_records` claim may retain this nonsecret in-progress cross-system reference in its existing `result_ref` metadata; it must be durable and bound to the approved actor/operation/key/fingerprint **before** the Keycloak call. This is not a second identity authority, new GRC marker store, table or column. If the implementation cannot durably bind and recover the same marker through the canonical idempotency mechanism, it must stop before invoking Keycloak; it must not generate a different marker on replay.

The fixed Keycloak adapter create method sends the marker in the user's `attributes` **within the single user-create payload**. Creating the user and then adding the attribute in another call is prohibited. Keycloak 26.7.5's Admin Users resource accepts profile attributes in create and supports custom-attribute query through `q`; MI6D must prove that the target realm's user-profile rules accept and preserve this attribute, that the approved service account can query and view it, and that the adapter can read it back without expanded authority. No Keycloak runtime setting is changed by this contract. The adapter may perform this fixed internal lookup as a helper of `createManagedUser`/`getManagedUser`; no caller-controlled Admin path or method is exposed.

On a same-key replay or uncertain create result, the backend first recovers the **same** marker from the durable claim and queries Keycloak by that attribute. It inspects the actual returned marker values and the complete result set; a truncated page, incomplete visibility or query error cannot prove uniqueness. Reconciliation is positive only for **exactly one** user with the exact marker and nonsecret attributes compatible with the original operation. Zero matches do not justify adoption by username, email, name, timestamp or similarity. More than one match, any contradictory metadata, missing stable subject or inability to establish complete visibility fails closed with `TCDX.CONFLICT.RECOVERY_REQUIRED`; no first/latest selection, second create or credential action follows. A zero-match retry is allowed only when the prior create is **proven not to have occurred** and the canonical claim still owns the same marker; otherwise return recovery required. A different idempotency key cannot adopt an existing username by marker or other inference.

After one proven match, its immutable Keycloak subject plus the exact configured issuer `https://iam.grc.tecdex.net/realms/tcdx-managed-identity` alone resolves/creates the canonical GRC `UserIdentity` under the existing uniqueness and audit/idempotency contract. The marker never substitutes for issuer or subject. The original Provision may report success only after the Keycloak user exists, that canonical mapping and safe audit/idempotency result are committed, no contradiction exists, and the original response remains under backend control. Reconciliation may finish the identity mapping but never reconstructs or re-discloses a lost temporary credential; an unconfirmed credential step returns recovery required and a later authorized PasswordReset uses a **new** Idempotency-Key. Same-key replay never repeats a credential change. After canonical resolution the marker may remain on the Keycloak user as inert metadata; removal is neither required nor an additional operation. It has no future authentication, authorization, RBAC, membership, tenant or commercial role.

MI6D must test the single-create payload, durable pre-call marker binding, exact-one/zero/multiple/contradictory/incomplete-visibility cases, crash before and after create, no username/email adoption, no repeated credential action, and no marker in public API or audit secrets. This decision adds no ninth MI6 operation, endpoint, schema change or runtime mutation in MI6F-R.

MI6 may use a separate confidential service-to-service Keycloak Admin API client in the managed realm with only proven permissions for create/read safe metadata, enable/disable, temporary credential reset, TOTP removal and logout. It cannot reuse `tcdx-grc` or receive unrestricted `realm-admin`, `manage-realm`, `manage-clients`, impersonation or global event-view authority. If Keycloak requires materially broader privilege, MI6 stops absent a human-approved, fully governed exception under rector 43 §5.4; MI6E records the specific conditional exception below. The client is not a GRC RBAC actor; every GRC command authorizes the human Platform actor **before** any Admin API call.

MI6 acceptance tests must cover absent/inactive PlatformRoleAssignment, each missing Permission, Tenant Admin from either of two tenants, Platform Support, supplied tenant header/body/query, wrong issuer/subject, duplicate username/identity, same/different idempotency key, uncertain provider outcome, invalid state, missing reason, credential and session invalidation, no-mailbox onboarding/recovery, safe audit, and authenticated-but-ungranted DENY. No QA account or runtime action is authorized by this documentary section.

An authorized operator provisions a named person with an optional email field and a temporary, single-use initial credential. The human-approved delivery model is a **direct secure operator-to-person handoff** without mailbox. Keycloak forces password setup/change and TOTP enrollment; a real TOTP challenge then establishes acceptable proof. Provisioning alone grants no membership or role. The permanent password is chosen by the person and unknown to the operator. MI6 must document and verify the person's identification, bounded temporary lifetime, one-use handling and exact admin API/permission/audit mappings before that lifecycle is implemented; no email, ticket, Git, log, report or prompt carries a credential.

Recovery uses authorized reset, old-credential and session invalidation, forced password setup/change, factor invalidation/re-enrollment where applicable, fresh MFA proof and audit. MFA reset is a sensitive scoped operation and never exposes the old seed. No security questions or mailbox dependency. GRC admin authorization must precede Keycloak administrative action; giving a tenant operator unrestricted Keycloak Admin API access violates MI-010/011.

### MI6E — controlled technical privilege exception `MI6-SEC-001` (2026-10-02)

The human architecture/security authority approved the Keycloak 26.7.5 user `manage` capability **only as a technical capability exception** for a dedicated confidential Managed Identity service account.
