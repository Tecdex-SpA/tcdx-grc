## MI5A proof and MI5-R local profile (2026-10-01)

MI5A demonstrated on Keycloak 26.7.5 that the native `oidc-amr-mapper` emits signed ID-token `amr=["pwd","otp"]` only after the REQUIRED username/password and OTP executions completed. First TOTP enrollment emitted `amr=[]`; password-only and invalid OTP did not yield a completed login token. Cookie is DISABLED, so the current browser flow reprompts both factors for each authorization. `acr` is not standalone MFA proof. The sanitized runtime evidence is outside the repository at `/tmp/tcdx-grc-step23l-mi5a-mfa-proof-report.md`.

MI5-R creates the confidential `tcdx-grc` Keycloak client with Authorization Code and PKCE S256, exact callback `https://grc.tecdex.net/auth/callback`, exact issuer `https://iam.grc.tecdex.net/realms/tcdx-managed-identity`, ID-token audience `tcdx-grc`, no browser web origins and no post-logout redirect. Its protected secret is outside Git. The backend uses existing `/auth/login` with `provider=tcdx-managed-identity` and the existing `/auth/callback`; the Zoho path remains the default. Managed Identity alone requires the validated signed ID-token AMR array to contain `pwd` and `otp` and resolves only an existing active canonical `UserIdentity` by issuer+subject. GRC alone retains Membership, PlatformRoleAssignment and RBAC authority. This is a local backend implementation; no GRC QA deployment, schema change, MI6 work, UI branding or Phase 6 start is declared.

## MI6F temporary credential and safe recovery contract — partial closure (2026-10-02)

The human architecture/security approval closes the disclosure, no-persistence, replay and uncertain-result semantics for Provision and PasswordReset in executable contract 22 and OpenAPI 02. The backend generates a cryptographically strong temporary credential and sends it to Keycloak as a temporary password. Only the initiating Platform Admin can see plaintext in the **original successful HTTPS response**, with `Cache-Control: no-store`; same-key replay returns safe metadata with `credential_disclosed=false` and never generates or discloses a second credential. Keycloak forces change at first login; a fixed time-based expiry is not guaranteed. The subsequent operator-to-named-human delivery is external and authorized out of band; GRC implements no mailbox or delivery integration. A lost credential is replaced only by a new authorized PasswordReset with a new idempotency key. `TCDX.CONFLICT.RECOVERY_REQUIRED` distinguishes an uncertain outcome and prohibits automatic re-execution. MI7 may show the value only in volatile memory and must not persist or log it.

MI6F does **not** resolve the Keycloak-create crash window. The existing durable GRC idempotency record has no known Keycloak subject before create returns; a later username search cannot prove that a user belongs to that original operation. No approved nonsecret operation marker exists on the Keycloak user, and MI6F does not introduce one. Thus `PROVISION_PARTIAL_FAILURE_RECONCILIATION=BLOCKED_PENDING_MARKER_DECISION`, `SAFE_TO_RESUME_MI6D=NO`, and `STEP_23L_MI6F_TEMPORARY_CREDENTIAL_RECOVERY_CONTRACT=BLOCKED_RECONCILIATION_MARKER_DECISION`. A human decision must define any opaque marker and its exact lifecycle before implementation resumes. MI6-SEC-001 remains effective and unchanged; no runtime, Keycloak, QA DB or schema mutation is part of MI6F.

## MI6F-R reconciliation marker decision — documentary closure (2026-10-02)

The later human architecture decision closes **only** MI6F's pending marker question. Contract 22 now fixes `tcdx_provision_reconciliation_marker`: backend CSPRNG, high-entropy opaque nonsecret value, durably bound to the existing idempotency claim before the provider call, and included as a Keycloak user attribute in the **single create mutation**. It is independent of the client Idempotency-Key and functional/person/tenant data; it is not an identity or authorization key. On an uncertain result, exactly one compatible Keycloak marker match with a stable subject may complete canonical issuer+subject resolution. Zero without proof of non-creation, multiple matches, contradictory data, query/visibility uncertainty and missing subject fail closed with the existing recovery-required error. A lost credential is never recovered or re-disclosed; a new authorized PasswordReset with a new key is the recovery path.
