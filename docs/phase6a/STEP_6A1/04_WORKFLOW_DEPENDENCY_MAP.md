Lifecycle authority is rector 21, the published LifecycleTransitionDefinition registry and existing operation permissions. Retention updates/transitions use strong If-Match; other transitions serialize expected_version from the selected current row/version. Idempotency-Key remains per command. No edit-status operation, frontend state authority, alternate lifecycle, hidden approval or automatic verification is recommended. Evidence approval/rejection binds the selected EvidenceVersion; completion of Action remains different from verification.

Current UI actions depend only on the current state, and backend revalidates permission/scope/SoD. Contextual enablement may reflect existing backend authorization projections for presentation, but must not imply that a visible button is an authorization grant. Object/SoD decisions stay server-authoritative. `controlAssessmentSubmit` owned_object is explicitly fail-closed because actor-to-Subject ownership is not canonically resolvable; a published tenant grant can authorize. UX must explain this limit, never fabricate ownership.

## Existing child read projections omitted from detail rendering

`apps/backend/src/core-grc/repository.ts:318` supplies SoA.items, AssuranceTest.samples, Evidence.versions, EvidenceVersion.links/reviews, Issue.origins and Action.evidence_links/verifications. The generic DetailDrawer filters out arrays/objects and does not fetch evidenceVersionGet for review/link display. These are available canonical projections, not missing persistence. ControlDetailContent renders normative/applicability relations but omits full scopes/objectives/crosswalk history and shows owner only as “Subject vinculado”. Render authorized relevant children and human labels before suggesting any new read endpoint.

No Risk/Incidents/Loss edges are implemented or designed here. Their columns may exist in canonical IssueOrigin projections; this does not authorize Phase 6 origins or workflows. Existing Phase 5 issueCreate permits only its three typed Core origins.
