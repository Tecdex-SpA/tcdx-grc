## Authorization, paging, filters and empty states

- Core collections: cursor pagination, default 25/max 100; applicable typed filters come from `apps/backend/src/core-grc/model.ts`. Common lifecycle filter exists, but ordinary collections do not expose text search. Human labels for assessments/applicability require composition with their authorized parent reads. Tenant membership + permission-specific scope + entitlement are required before list/detail; tenant data is re-filtered in the repository. Global Controls/Requirements use explicit pack visibility, never unrestricted global search.
- Subjects: `GET /api/v1/subjects`, `organization.subject.read`, CORE_PLATFORM/tenant. Search (`filter[query]`, 2–160 characters), type and cursor; only active, effective, non-superseded subjects. Source `apps/backend/src/core-grc/subject-read.ts:15`. `SubjectSelect` currently uses first 100 results and has no pagination/empty explanation. Controls owner uses this component; other owner/scope fields currently remain text inputs. Tenant-admin-only `subjectCreate` is an explicit separate operation; a picker must not silently create a Subject.
- Requirement selection: `requirementList` needs known FrameworkVersion; queries by code/editorial summary/locator, normative unit and cursor. Pack and selected tenant visibility is enforced in `apps/backend/src/regulatory/tenant-read.ts`. The handler does not automatically exclude historical requirements by current effective interval; the UI must not invent an eligibility rule. Reference selection should explain version/period and obey the approved command contract.
- Controls/versions: `controlList` supports query, framework, owner/scope and lifecycle filters; `controlGet` supplies authorized versions. Existing `ControlVersionSelect` filters global/platform references, loads first 100 controls, then chooses the first returned version. For assessments/tests, use a tenant instance and its matching version; do not reuse the base-control restriction as a tenant-control picker. Concurrent/stale selection requires command revalidation.
- Methodologies: separate domain registries, published/effective/compatible formulas only; tenant read permission and capability still mandatory although rows are platform-owned. `MethodologySelect` consumes all cursors and provides loading/error/empty text. The contract allows selection; no rule proves that one version must be chosen automatically. Source `docs/executable-contracts/27_PHASE5_METHODOLOGY_BINDING.md` and `apps/backend/src/core-grc/methodologies.ts`.
- Memberships: `membershipList`/`membershipGet` use `platform.membership.read`. Tenant mode requires validated selected tenant; Platform mode is an independent administrative flow and supplies no tenant business authorization. Cursor list has no name search or active-membership filter; returns nested identity labels and role history. `assertTenantMembership` checks existence/same tenant, not active state. Do not add an unapproved active-only assignment invariant. Empty picker needs an explanation and a permission-aware route to existing user administration, never an automatic invite/grant.
- Evidence versions: `evidenceList` → `evidenceGet.versions` → `evidenceVersionGet`; human label from Evidence code/version. Fulfillment/closure requires approved version and acceptable scan (`assertEligibleEvidenceVersion`), and fulfillment additionally requires a matching typed EvidenceLink. Full version list/search is not a prerequisite to a contextual picker: existing scoped reads can compose the candidates. No new unrestricted version endpoint is recommended.
- Retention: `retentionPolicyList/Get` require `privacy.retention_policy.read` + PRIVACY/tenant. Publication/expiry semantics are not equivalent to mere existence. Core list uses a tenant-only predicate, whereas upload/evidence reference validation accepts global/same-tenant policy. A selector must make ownership, version and policy kind clear, distinguish inaccessible data from no data, and wait for any missing retrieval authority below. Policy creation remains a separate explicit PRIVACY command with SoD.
- FileObject: current upload pipeline already derives its UUID from finalize/scan; use context, filename and scan feedback. No FileObject list operation was found. The existing browser upload solves the normal create path; an existing-file browser is not presumed required. Download is permission/tenant checked; no direct storage URLs, SQL or arbitrary object key.

All lookup errors remain errors; 403 is not a valid empty collection. If the actor cannot read a required reference, explain the prerequisite; a create permission never implies its read permission. Reset dependent selection on parent or tenant change, cancel stale requests, retain selected human context and serialize only authorized canonical IDs. Do not carry a cached selection across tenants. Generic core cursor hashes bind filters rather than tenant, while SQL always scopes the tenant; UI caches must therefore include tenant regardless of cursor implementation.
