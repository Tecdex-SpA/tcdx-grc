# Estados vacíos, prerequisitos y fronteras RBAC

Fecha: 2026-10-08. Autoridad: TCDX_GRC_MASTER_REGENT_BASELINE_v1.7_2026-09-23. HEAD: main / 6af66387aa03fa185ef139584de07700f247b903. Alcance: diseño documental, sin implementación.

Tenant activo validado → Membership activa → entitlement → Permission → scope → ObjectPolicy → SoD → ALLOW; default DENY. PlatformRoleAssignment no sustituye MembershipRole. La API revalida cada lectura y comando.

Fuentes: `docs/rector/baseline/22_RBAC_PERMISSION_SCOPE_MATRIX.md`, `docs/executable-contracts/13_AUTHENTICATION_AUTHORIZATION_CONTRACT.md`, `docs/executable-contracts/23_FRONTEND_AUTHENTICATION_AUTHORIZATION_PROJECTIONS.md`, `docs/phase6a/STEP_6A1/04_WORKFLOW_DEPENDENCY_MAP.md`. Todos SEL/LINK/FORM aplican esta política común y su restricción específica; no selector universal sin políticas de entidad.

| Estado | Evidencia diferenciadora | Mensaje empresarial | Acción permitida / comportamiento |
| --- | --- | --- | --- |
| ES-A No registros | Lectura autorizada exitosa vacía, no error | No hay [entidad] disponibles en este contexto. | Crear sólo si operación canónica/permiso independiente; de otro modo orientación al responsable. |
| ES-B No elegibles | Lectura autorizada con resultados pero filtro elegibilidad explícito excluye | No hay [entidad] que puedan utilizarse en esta operación. | Explicar condición demostrada (p.ej. versión approved para fulfillment), no inventar publicación/estado; modificar filtro visible si legítimo. |
| ES-C Sin permiso | Proyección backend deny o 403; no consultar objetos para construir mensaje | No tienes acceso a esta operación en el tenant seleccionado. | Ocultar datos/acciones no autorizados; orientar al administrador del tenant. Sin conteos/existencia ajenos ni elevación automática. |
| ES-D Configuración inexistente | Resolución autorizada insuficiente/no effective configuration | No hay una configuración efectiva disponible para este contexto. | Distinguir optional sin configuración de requerida por metodología. Si requerida bloquear; conflicto 409 requiere revisión autorizada, nunca elegir capa arbitraria. |
| ES-E Catálogo no publicado | Fuente aprobada prueba estado/vigencia o Pack no habilitado en contexto visible | No hay una versión publicada o habilitada disponible para este contexto. | Mostrar sólo orientación compatible con permission de la gestión existente; no new publish command ni datos de packs inaccesibles. |
| ES-F Bloqueado por estado | Estado canónico + transición de registry/permisos | Esta acción requiere [estado empresarial publicado]. | Mostrar acción previa autorizada cuando existe, no editar lifecycle_state ni ejecutar cadena automática. |
| ES-G Lectura temporal fallida | ApiProblem de timeout/transporte/servicio/retryable | No pudimos cargar las opciones. Intenta nuevamente. | Retry explícito, preservar entrada válida y no aceptar datos obsoletos; no vaciar como éxito ni fallback de otro tenant. |

Apply individual dependency: 02 tiene 29 filas con estado/permiso/contexto y ES-A/G; 03 tiene todos los 95 FIELD_ID agrupados; 07 tiene los 42 formularios y prerequisitos. ES-C siempre prevalece sobre explicación detallada de existencia. ES-D/E sólo se explica con fuente autorizada que demuestre motivo; ausencia de permiso no permite distinguir inexistente/inactivo. Child records pueden mostrarse desde proyección del padre sólo si ese contrato concede su visibilidad; no inferir que permiso de escritura da permiso de lectura independiente.

## Prerequisito faltante y retorno

Comprobar primero si existe operación en OpenAPI/matriz. Comprobar entitlement/Permission/scope/ObjectPolicy y SoD para esa operación, independientemente del formulario dependiente. Si hay ambos: acción visible Crear [entidad] → formulario canónico explícito → success leído → volver y proponer selección del nuevo registro, sin guardar dependiente automáticamente. Si no hay operación: orientación sin botón de creación ni ruta inventada. Si no hay permiso: orientación sin mostrar objeto inaccesible. Ejemplos existentes permitidos condicionados: Issue → actionCreate, Control → controlAssessmentCreate/assuranceTestCreate, Applicability → requirementAssessmentCreate. No framework creation, nueva metodología, Document management ni Membership invite desde este diseño sin contrato existente validado.

## Tests negativos reutilizables

N-01: usuario sin Membership activa y sólo PlatformRoleAssignment no accede a selector tenant. N-02: tenant A con UUID/label/cursor de B devuelve deny/no data, nunca nombre/count. N-03: entitlement vencido/Pack no habilitado quita opciones/acciones sin grants nuevos. N-04: permiso read no autoriza create/update/transition, permiso create no otorga lookup administrativo. N-05: scope limitado no amplía tenant-wide; ObjectPolicy evalúa elegido y parent/context antes de submit. N-06: submitter Evidence no aprueba propia versión; completer/assignee Action no verifica cuando SoD lo prohíbe. N-07: estado fuente cambiado después de abrir → backend rechaza, UI refresca y conserva entradas sin overwrite. N-08: tenant cambiado durante request invalida cursor/cache/selección/respuesta tardía; labels no pasan al nuevo tenant. N-09: denegación de dependencia no se convierte en lista vacía ni llamada a endpoint global. N-10: ownership Control global no se presenta como implementación tenant; owner Subject no se convierte en Membership. N-11: owned_object controlAssessmentSubmit sin mapping actor↔Subject permanece DENY; sólo grant publicado puede autorizar. N-12: upload sin scan PASS/no policy autorizada no permite evidenceCreate; no URL firmada/secretos en error/log/UI persistida.

Tests por selector/links deben incluir paginación >100, duplicados de label, selección previa expirada, optional omitido, empty vs error, 409/retry con misma intención, accesibilidad label/aria-error/foco y narrow viewport. Backend sigue autoridad; browser projections sólo presentación.
