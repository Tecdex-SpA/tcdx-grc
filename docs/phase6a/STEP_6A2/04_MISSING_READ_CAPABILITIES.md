## RR-G01 — FrameworkVersion para Compliance

Necesidad: FORM-01/08 y explorador Requirement sin obligar permiso Controls. Cercana: controlList.framework_filters presenta versiones/nombres/ediciones sólo bajo controls.control.read/CONTROLS_ASSURANCE; reutilizable exclusivamente si actor está autorizado, no como dependencia implícita de Compliance. Lecturas de asignación Pack no equivalen a FrameworkVersion.

DRAFT: lectura de FrameworkVersion autorizadas para el tenant activo: referencias globales habilitadas por Pack/entitlement/ObjectPolicy y versiones internas del mismo tenant que el modelo permita; nunca todas las globales. Respuesta mínima propuesta: identidad FrameworkVersion, identidad/nombre/code de Framework, edition/version label, ownership y datos de vigencia/publicación/procedencia ya existentes necesarios para elegibilidad. Confirmar nombres exactos en modelo/contrato antes de publicar, sin añadir columnas. ID opaco como value, nombre + edición como label.

Filtros propuestos: búsqueda por nombre/code/edición y padre Framework, cursor/page_size limitado; validar filtros contra columnas canónicas existentes. Orden estable con desempate ID a definir en publicación; cursor ligado tenant/consulta. Excluir no autorizados antes de contar/paginar. Política de lectura debe usar Permission publicado compatible; compliance.framework.read aparece como recurso potencial en rector22 pero NO como Permission publicada encontrada en catálogo vigente: no crear ni conceder implícitamente. Owner Compliance + Architecture + Security define/pública mapping exacto antes de implementación. No reutilizar controls.control.read para ampliar autoridad.

Pruebas: lector Compliance sin Controls no queda obligado a obtener grant ajeno; cross-tenant, pack no habilitado, interno ajeno, Membership/entitlement inactivos, cursor tenant distinto, pagina >100 y selección expirada. Si no existe versión: ES-A/E, sólo navegación de gestión a operación ya existente y autorizada; no crear framework en silencio.

## RR-G02 — EffectiveConfiguration contextual

Cercana aprobada: effectiveConfigurationGet, GET /api/v1/effective-configurations/{id}, configuration.effective_configuration.read, CORE_PLATFORM, scope tenant/objeto. Contrato declarado no equivale a ruta implementada/discovery. `apps/backend/src/configuration/resolver.ts` resuelve arrays de layers y retorna value/selectedLayerId/layerIds; no expone selector HTTP ni identidad de snapshot reutilizable.

DRAFT: reutilizar detail aprobado y añadir capacidad de resolución/discovery por contexto de evaluación conforme a config.effective_configurations y reglas rector29, sin escribir configuración desde el formulario. Inputs deben mapear solamente a definición/version, scope/objeto y effective instant canónicos establecidos por el modelo; Architecture/Domain Owner debe cerrar binding exacto entre esos elementos y RequirementAssessment/ControlAssessment antes de exponer adapter. No inventar un endpoint resolve ni persistir el resultado de la función como otra entidad.

Salida mínima propuesta: identidad snapshot EffectiveConfiguration existente o result insuficiente/conflict; identidad y versión de definición publicada, scope/contexto, effective instant y provenance de layers ya canónicos, resumen legible autorizado. No mostrar secrets/value JSON al usuario ni dejar que elija por UUID. Resolver determinísticamente sólo cuando las reglas publicadas producen un único resultado; 409 por conflicto no se resuelve eligiendo primera layer; 422/no effective configuration se explica ES-D. Resolución singular no requiere paginación; si se autoriza discovery de snapshots, especificar cursor/filtros tenant/definition/scope/tiempo y orden estable en contrato, no listado irrestricto.

Permiso existente configuration.effective_configuration.read conserva scopes/ObjectPolicy; no grant desde create assessment. Campo optional: omisión contractual es legítima si el usuario conoce que no se aplica configuración adicional y la metodología admite ese caso; no omitir automáticamente para evadir binding. Si se exige configuración por reglas efectivas y no existe, bloquear y orientar a quien tiene operación canónica, sin inventarla. Methodology sigue obligatorio y separado.

Pruebas: mismo tenant/definition/domain compatible; conflicto de precedencia, sin layers, scope ajeno, snapshot histórico versus actual, payload optional ausente y case que exige binding; resolver no crea layer/config entidad ni redefine outputs.

## RR-G03 — TenantMembership como responsable empresarial

Cercanas: membershipList/Get con platform.membership.read. Tenant Admin usa tenant autenticado; Platform Admin tiene flujo administrativo explícito independiente, no bypass del selector tenant. Reuso administrativo sólo si el usuario ya cumple su política, proyectar mínimo; no imponer rol admin para asignar EvidenceRequest/Action.

DRAFT: proyección mínima de TenantMembership del tenant activo destinada a selección de responsable autorizada por políticas de EvidenceRequest/Action. value Membership ID, label nombre visible de UserIdentity autorizado + indicador de elegibilidad necesario; no exponer email, identity key, role assignments, credentials, roles/grants, ni IDs de identidad adicionales. Nombre duplicado se desambigua únicamente con atributos no sensibles autorizados por el contrato aprobado; nunca obligar a copiar ID.

Scope: Membership activa del lector, entitlements del dominio, scope/ObjectPolicy de operación destino. Seguridad debe aprobar permiso de lectura exacto existente o demostrar y publicar necesidad de nuevo Permission antes del código; create por sí mismo no equivale a read IAM. Selección target membership: handlers actuales verifican existencia/mismo tenant, no se ha demostrado guard activo-only para asignados. Owner IAM/Domain debe cerrar elegibilidad de asignado sin agregar restricción semántica desde UI. Actores de requested_by/executor/reviewer server-owned usan label de proyección autorizada; no picker editable.

Filtros DRAFT: búsqueda por display label autorizado, cursor/page_size bounded, orden estable label+Membership ID definido al publicar; evitar endpoint de búsqueda UserIdentity global. Vacío/denegado ES-A/C sin número de personas inaccesibles. No invitar/crear Membership silenciosamente. Sólo mostrar creación si operación IAM canónica y permisos exactos ya autorizados para usuario.

Pruebas: usuario de dominio sin admin, tenant distinto/cursor, Membership lector suspendida, target inactive conforme a decisión publicada, labels ambiguos, cambio tenant durante request, minimización de atributos, PlatformRoleAssignment sin Membership no da acceso empresarial.

## RR-G04 — RetentionPolicy seleccionable en Evidence/upload

Cercanas retentionPolicyList/Get: privacy.retention_policy.read + PRIVACY, lectura actual tenant-only. evidenceCreate/upload admiten política global autorizada o same-tenant; la lista actual no prueba descubrimiento global ni permiso de Evidence reader. Reuso únicamente para usuario con autoridad Privacy existente y para filas elegibles que realmente cubra.

DRAFT: proyección mínima de privacy.retention_policies para propósitos upload/evidence bajo política de objeto gobernada; global autorizado y same-tenant, sin grant de modificación global. value RetentionPolicy ID; label policy_code + versión + policy_kind, duración/trigger, mandatory/precedencia y vigencia/status existentes para explicar el efecto. No inventar política, duración legal o tabla lookup.

Owner Privacy/Legal + Evidence + Security debe cerrar (a) qué estados/vigencias hacen la política seleccionable en cada operación, sin inventar published-only; (b) cómo permission/entitlement permite mínima lectura a Evidence reader sin acceso Privacy amplio; (c) definición de visibilidad global. Reusar Permission publicado sólo si su definición lo autoriza; caso contrario decisión y publicación contractual antes de código, sin broad grant por defecto. Filtros DRAFT por code/version/kind y elegibilidad propósito; cursor/page_size bounded, orden estable contractual, filtering ObjectPolicy antes de paginar.

FileUploadIntent y Evidence deben conservar policy ID elegido y compatibilidad temporal; si elección cambia después de finalización, revalidar contrato y no reasignar metadata silenciosamente. No sustituir con política de otro tenant o preset ficticio. Vacío ES-A/B/D; crear política sólo retentionPolicyCreate con PRIVACY/permiso y confirmación explícita, no preselección de draft no elegible.

Pruebas: global permitido/denegado, tenant ajeno, Evidence-only vs Privacy-authorized, políticas no elegibles/históricas, cursor, policy cambiada, upload + evidence mismo contexto, selección única visible sólo si permitida por contrato.
